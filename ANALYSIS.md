# Анализ проекта NetView

> Дата анализа: 04.08.2026
> Анализ проводился по исходному коду и данным, полученным напрямую от всех четырёх внутренних сервисов (Printer Monitor :8101, Host Monitor :8102, LogSpy :8103, NetCerber :8104 — все доступны, HTTP 200).

---

## 1. Обзор

**NetView** — веб-панель мониторинга IT-инфраструктуры на Flask 3 + Jinja2 + TailwindCSS (CDN) + HTMX. Агрегирует данные из трёх микросервисов (принтеры, хосты, логи Squid/AD, стоп-лист) и четвёртого — NetCerber (устройства локальной сети).

| Компонент | Технология |
| --- | --- |
| Backend | Flask 3.1.1, uvicorn 0.34.0 (ASGI-мост) |
| Фронтенд | Jinja2, TailwindCSS 4 (CDN), HTMX 2.0.4, FontAwesome 6 |
| Запуск | Docker (python:3.12-slim) + `run.py` для локального запуска |

Структура проекта чистая: клиенты API (`app/api/`), blueprint'ы (`app/routes/`), шаблоны (`app/templates/`). Код в целом читаемый и единообразный.

## 2. Корректность отображения данных

Ниже — проверенные по реальным ответам API несоответствия между тем, что возвращают сервисы, и тем, что показывается в UI.

### 2.1. Критично: статус принтеров отображается красным у ВСЕХ устройств

- API возвращает статусы в нижнем регистре: `"ok"`, `"low_toner"`, `"offline"`.
- Шаблон `app/templates/partials/_printer_list.html:73` проверяет `printer.status == 'OK'` (верхний регистр) — **условие никогда не выполняется**, и зелёный бейдж не рендерится ни для одного принтера. Исправные принтеры выглядят как неисправные.

**Файлы:** `app/templates/partials/_printer_list.html:73`.

### 2.2. Расхождение счётчика «Низкий тонер» на Dashboard

- Dashboard (`app/routes/dashboard.py:38-41`) считает низкий тонер по жёстко зашитому порогу `< 20` и **включает офлайн-принтеры** (у них `toner_percentage_value = 0.0`).
- Сервис использует настраиваемый порог `alert_threshold = 10` и статусы `low_toner`.
- Фактически: по данным API порогу `<20` соответствуют **10** принтеров (из них 3 офлайн), а сервис сообщает **6** принтеров с низким тонером (`low_toner_printers: 6`).
- Итог: цифра на карточке Dashboard не совпадает ни с данными сервиса, ни с настройкой порога (см. раздел «Настройки»), где порог отображается как 10%.

**Файлы:** `app/routes/dashboard.py:38-41`, `app/routes/settings.py:32-39`.

### 2.3. Расхождение количества записей в логах Squid

- В `app/routes/logs.py:56` записи фильтруются на стороне UI: `records = [r for r in raw_records if r.get("user") and r["user"] != "-"]` (скрываются записи без пользователя).
- При этом `pagination.total_records` (из API) остаётся без учёта этой фильтрации. Например, реальные данные: API возвращает `total_records: 482492`, а в таблице показывается только часть строк с пользователями.
- Итог: заголовок «Записи (482492 всего)» и количество строк в таблице не соответствуют друг другу; пагинация по страницам не совпадает с реально отображаемым списком.

**Файлы:** `app/routes/logs.py:56`, `app/templates/logs.html:106`.

### 2.4. «Тихие нули» при недоступности сервисов

Почти все запросы к API обёрнуты в `except Exception: pass` / пустые списки. Если сервис недоступен, UI показывает нули/пустоту **без каких-либо индикаторов ошибки**:

- Dashboard: `принтеров=0`, `хостов=0` — выглядит как «нет данных», а не «сервис недоступен».
- `settings.html` — индикатор статуса сервиса есть (зелёный/красный), но остальные страницы — нет.
- Пользователь не может отличить «реально ноль» от «сервис лежит».

**Файлы:** `app/routes/dashboard.py:42-44, 53-56`, `app/routes/hosts.py:47-49`, `app/routes/users.py:65-67` и др.

## 3. Слабые места

### 3.1. Безопасность (высокий приоритет)

1. **Отсутствие аутентификации и авторизации.** Любой, кто имеет доступ к порту 5000 по сети, может:
   - просматривать данные мониторинга (списки пользователей AD, IP, логи, hosts);
   - изменять стоп-лист, пороги, интервалы;
   - авторизовывать/деавторизовывать устройства NetCerber, запускать сканирование сети, удалять записи сканирований;
   - загружать/удалять эталонный снимок.
   Для внутренней панели это как минимум риск, для внешнего контура — критическая уязвимость.
2. **Потенциальный Stored-XSS через стоп-лист.** Слово выводится внутри JS-контекста: `onclick="removeWord('{{ word }}')"` (`stoplist.html:25`). Jinja-escape `&#39;` внутри HTML-атрибута декодируется браузером в `'`, что позволяет выйти из строки и выполнить произвольный JS (например, слово вида `x');alert(1);//`). Учитывая п.1 (нет аутентификации), это эксплуатируемо без особых усилий.
3. **Нет защиты от CSRF** на всех изменяющих endpoint'ах (`/stoplist/add`, `/settings/htmx/*`, `/netcerber/htmx/*` и др.).
4. **Жёстко зашитый `SECRET_KEY`** (`"change-me"`) и `DEBUG = True` в конфиге по умолчанию (`app/config.py:14,20`).
5. **Жёстко зашитые IP-адреса сервисов** в конфиге — нет чтения из переменных окружения, что усложняет безопасное развёртывание (секреты и адреса должны конфигурироваться вне кода).

### 3.2. Производительность

1. **Последовательные синхронные HTTP-запросы на Dashboard.** Страница делает ~6 запросов к 3 сервисам друг за другом. При недоступности сервиса время ответа страницы может составить сумму таймаутов (10–20 с и более на сервис).
2. **Тяжёлый запрос сводки логов при каждой загрузке Dashboard.** `GET /api/v1/summary` возвращает ~600 КБ данных (реальный замер: HTTP 200, 612 КБ) и парсится на каждой загрузке главной страницы.
3. **Нет кэширования** и «шардок» агрегатов. Логи (482 тыс. записей в текущем файле) каждый раз обрабатываются заново.
4. **Нет переиспользования HTTP-сессии** (`requests` создаёт новое соединение на каждый вызов).
5. Сортировка хостов выполняется **на клиенте только по текущей странице (50 записей)** — при большом количестве хостов сортировка не является глобальной.

### 3.3. Надёжность и обработка ошибок

1. Массовое использование `except Exception: pass` — проглатываются все ошибки без логирования. Диагностика отказов затруднена.
2. Нет retry и no-фолбэков: любой сбой запроса → пустой список/нули.
3. `app/routes/netcerber.py` использует `request.args.get("authorized", type=bool)` — зависит от строкового формата `"1"`/`"0"`; стоит передавать явно.
4. Нет таймаут-политики, единой для всех клиентов (20/10/15 с — разные).

### 3.4. Поддерживаемость и качество кода

1. **Мёртвый код:**
   - `@app.before_request log_unknown_requests` — заглушка (`pass`), `app/__init__.py:58-61`.
   - Маршрут `netcerber.hmtx_alerts` и шаблон `partials/_netcerber_alerts.html` нигде не связаны с UI (нет страницы/ссылки на оповещения).
2. **Нет тестов, нет CI, нет линтера/типизации** (`py.typed`/mypy/ruff не настроены).
3. **Неконсистентность README и Makefile:** README указывает `./venv/bin/python run.py`, Makefile — `./.venv/bin/python run.py`.
4. **Нет конфигурации через env**: адреса сервисов, порт, `SECRET_KEY` захардкожены; для Docker развёртывания пришлось бы править код.
5. Дублирование вспомогательных функций `_get_*_client()` в каждом blueprint'е (незначительно).
6. `run.py` запускается с `debug=True` — в проде следует использовать только uvicorn/Docker.

## 4. Положительные стороны

- Чёткая структура: клиенты API ↔ blueprint'ы ↔ шаблоны.
- Единообразный стиль кода, докстринги в модулях.
- Активное использование HTMX (обновление частичных списков без полной перезагрузки).
- Тёмная/светлая тема, аккуратная вёрстка Tailwind.
- Корректная обработка отсутствующих значений через `default()`/`or '—'` в большинстве мест.
- Пагинация с умным сокращением номеров страниц в логах.
- Graceful-degradation в части рендеринга: страницы не падают при недоступности сервисов (но см. п. 2.4).

## 6. Заключение

Проект структурно аккуратный и функционально насыщенный, но имеет **две подтверждённые ошибки отображения данных** (статус принтеров всегда красный; счётчик низкого тонера и количество записей логов не соответствуют реальности), **отсутствие аутентификации** и **наличие потенциального XSS**. Основные риски — безопасность и достоверность отображаемых метрик. После устранения пунктов «Приоритет 1» панель можно считать готовой к эксплуатации во внутренней сети.
