# Анализ проекта NetView

> Дата анализа: 19.08.2026
> Верификация: статический анализ исходного кода (Python 3.12, Flask 3.1.1, Jinja2, HTMX).
> Статус: P1 ✅, P2 ✅, P3 ✅ — выполнены (19.08). Осталось: CI (GitHub Actions).

---

## 1. Обзор

**NetView** — веб-панель мониторинга IT-инфраструктуры на Flask. Агрегирует данные из четырёх
внутренних сервисов (Printer Monitor, Host Monitor, LogSpy, NetCerber), отдаёт единый интерфейс
на Jinja2 + TailwindCSS (CDN) + HTMX.

| Компонент | Технология |
| --- | --- |
| Backend | Flask 3.1.1, uvicorn 0.34.0 (WSGI-мост через `WSGIMiddleware`) |
| Фронтенд | Jinja2, TailwindCSS 4 (CDN), HTMX 2.0.4, FontAwesome 6 (CDN) |
| Запуск | Docker (`python:3.12-slim`) + локальный `run.py` |
| Код | ~2100 строк Python, 38 файлов (8 роутов, 4 клиента API, 30 шаблонов) |

### Структура

```
app/
├── __init__.py        # фабрика create_app, фильтры шаблонов (datetime, human_size, time_ago)
├── config.py          # конфигурация (всё захардкожено, см. §5)
├── api/               # 4 HTTP-клиента: printer, host, logspy, netcerber
└── routes/            # 8 blueprint'ов: dashboard, printers, hosts, logs, netcerber, settings, users, stoplist
```

---

## 2. Что сделано хорошо

1. **Чистая структура** — фабрика приложения, blueprint'ы, отдельный слой API-клиентов. Разделение ответственности понятное, легко расширять.
2. **Документация** — у каждого модуля и публичного метода есть docstring; комментарии на русском, по делу.
3. **Graceful degradation** — при недоступности сервиса страницы не падают, показывают баннер «Сервис недоступен» вместо тихих нулей. Это правильный паттерн для агрегатора.
4. **Фильтры шаблонов** — `human_size`, `time_ago`, `datetime` — аккуратные, обрабатывают `None` и строки.
5. **HTMX без JS** — интерфейс асинхронный, но держится на серверных фрагментах; просто и надёжно.
6. **Аккуратный `.gitignore`** — секреты, venv, кэш, логи исключены.

## 3. Критичные проблемы (P1)

### 3.1. Полное отсутствие аутентификации и CSRF-защиты

Панель доступна любому, кто может достучаться до порта 5000. При этом она **не read-only**:

- `/stoplist/add`, `/stoplist/remove`, `/stoplist/replace` — изменение стоп-листа
- `/netcerber/htmx/authorize*`, `/htmx/set-baseline`, `/htmx/delete-scan` — управление авторизацией устройств и удаление записей сканирований
- `/settings/htmx/threshold`, `/settings/htmx/interval` — смена настроек

Все POST-эндпоинты принимают `application/x-www-form-urlencoded` без токена — классическая CSRF-мишень
(достаточно ссылки/формы со стороны любого сайта во внутренней сети).

**Рекомендация (минимум):**
- Flask-Login (или даже базовая HTTP Basic через ограниченный набор пользователей) + `@login_required` на всех blueprint'ах, кроме health.
- Flask-WTF `CSRFProtect(app)` — он поддерживает HTMX (токен в заголовке `X-CSRFToken`).

### 3.2. Секреты и конфигурация захардкожены

`app/config.py`:

```python
SECRET_KEY = "<публичный ключ-заглушка>"   # все знали из репозитория
PRINTER_API_URL = "http://<внутренний-ip>:8101"   # и 8102/8103/8104
AD_DOMAIN = "<внутренний-домен>"
DEBUG = True
```

- Секретный ключ известен всем, кто видел репозиторий.
- Внутренние адреса сервисов зашиты в код — смена сети = правка исходников.
- `DEBUG = True` — в проде это утечка трейсбеков и работа отладочного дебаггера.

**Рекомендация:** вынести всё на переменные окружения через `os.environ.get(...)` (или `python-dotenv`),
`.env` уже в `.gitignore`. `DEBUG` по умолчанию `False`, включать только через env.

### 3.3. Баг: `type=bool` в query-параметрах NetCerber

`app/routes/netcerber.py:68-69`:

```python
authorized = request.args.get("authorized", type=bool)
unauthorized = request.args.get("unauthorized", type=bool)
```

Flask конвертирует через `bool(value)`, а `bool("false")` в Python — **True**.
То есть `?authorized=false` вернёт `True`, а `?authorized=0` — тоже `True`.
Фильтр «неавторизованные устройства» **никогда не работал правильно**.

**Исправление:**

```python
def _as_bool(value: str | None) -> bool | None:
    if value is None:
        return None
    return value.lower() in ("1", "true", "yes", "on")
```

## 4. Ошибки и слабые места (P2)

### 4.1. Хрупкий парсинг целых чисел — 500-е ошибки

`logs.py:32-33` и `users.py:211-212`:

```python
page = int(request.args.get("page", 1))   # ValueError при page=abc → 500
```

**Исправление:** `request.args.get("page", 1, type=int)` (Flask уже умеет).

### 4.2. Дублирование сортировки — три почти одинаковые функции

`hosts.py:_sort_hosts`, `printers.py:_sort_printers`, `netcerber.py:_sort_devices` — копипаст
с одним отличием (printers парсит строковые числа). Напрашивается один модуль `app/sorting.py`
с конфигурируемой картой полей, либо перенос сортировки в API-клиенты (им виднее — они же знают формат).

### 4.3. Дублирование клиентов

`LogSpyClient._get/_post/_put/_delete` (строки 24–57) и `NetCerberClient._get/_post/_patch/_delete`
(строки 24–58) — идентичные обёртки над `requests`. Вынести в базовый класс:

```python
class BaseApiClient:
    def __init__(self, base_url, timeout=15):
        ...
    def _request(self, method, path, **kwargs): ...
```

`PrinterMonitorClient` и `HostMonitorClient` тоже переписать на него — станет единый таймаут-поведение и точка для ретраев/логирования.

### 4.4. `_fmt_size` в `users.py` дублирует фильтр `human_size`

`users.py:134-139` — та же логика, что и в `app/__init__.py:49-67`. Либо вынести в общий модуль,
либо отдавать размеры и форматировать в шаблоне фильтром.

### 4.5. Тяжёлая страница деталей пользователя

`users.py:118-120` — `get_data(current_log, user=user_upn, limit=500)` тянет 500 записей только
чтобы посчитать статистику (плюс второй запрос на `blocked`). Если API отдаёт `stats`/`pagination`
с авторитетными счётчиками (а он отдаёт — код уже их использует), статистику можно собрать без
полной выгрузки записей. Особенно актуально на логах большого размера.

### 4.6. Список хостов ограничен 50

`hosts.py:48` — `get_hosts(page=1, limit=50)` и `total_pages` не используется. Если хостов >50 —
пользователь их не увидит, пагинация на странице `hosts.html` не работает, несмотря на HTMX-механизм.

### 4.7. Мёртвый код

`app/__init__.py:100-103` — `log_unknown_requests` с docstring и `pass`. Заглушка, которую забыли удалить. Убрать или реализовать.

### 4.8. Захардкоженный порог тонера в dashboard

`dashboard.py:48` — магическое число `20` (низкий тонер). Оно уже конфигурируется через `/settings`
(threshold), но здесь используется локальная константа. Согласовать с API (`get_threshold()`).

## 5. Архитектурные замечания (P3)

### 5.1. Dashboard: последовательные вызовы вместо параллельных

`dashboard.py` делает до **6 последовательных** HTTP-запросов к LogSpy (AD stats → logs → summary → stoplist),
плюс принтеры и хосты. При недоступности одного сервиса страница ждёт таймаут (10–20 с).

**Рекомендация:** параллелить через `concurrent.futures.ThreadPoolExecutor` или перейти на `httpx`
и гонять их одновременно. Таймауты уже есть в клиентах — этого достаточно для аккуратного
graceful degradation.

### 5.2. Нет .dockerignore — образ раздут

`Dockerfile` делает `COPY . .` — в образ попадают `.git` (и без `.dockerignore` вообще всё). 
Учитывая, что папка содержит `.venv` (~сотни МБ), образ наверняка тяжёлый.

**Исправление:** минимальный `.dockerignore`:

```
.venv/
__pycache__/
.git/
*.pyc
.env
ANALYSIS*.md
```

и точечные COPY: `COPY app/ ./app/ COPY run.py .`

### 5.3. ASGI-мост без выгоды

`app/asgi.py` — `WSGIMiddleware(create_app())`. Flask синхронный, поэтому uvicorn здесь не даёт
никакого выигрыша, только лишний слой. Для продакшена проще `gunicorn app:app` с несколькими
воркерами (или тот же uvicorn, но это равнозначно). Не баг, но стоит понимать.

### 5.4. TailwindCSS через CDN в проде

Зависимость от внешних CDN (Tailwind, HTMX, FontAwesome) — при недоступности интернета панель
теряет вид и функциональность. Для внутренней сети лучше собрать статику в `app/static/`
(или хотя бы `pip download` + локальная раздача). Бонусом — отключение «живого» Tailwind CDN
(он же JIT-компилятор в браузере) уменьшит расход трафика и нагрузку на клиентов.

### 5.5. Требования к тестам

Тестов нет вообще. Минимум, который быстро окупится:
- `pytest` + `pytest-flask`: юнит-тесты на сортировки, `human_size`, `time_ago`, парсер bool.
- Клиентов — через `responses` или `requests-mock`.
- Прогон в CI (GitHub Actions): `ruff check .` + `pytest`.

### 5.6. Линтер/форматтер

В `.gitignore` есть `.ruff_cache/`, значит ruff использовался, но в `requirements.txt`/`Makefile`
его нет. Закрепить: `ruff check app/` в Makefile и CI, добавить в `requirements-dev.txt`.

## 8. Вердикт

Проект в хорошей форме: архитектура понятная, код читаемый и документированный, аварийное
поведение при недоступности сервисов продумано. Главные риски — **операционные** (нет авторизации,
секреты в коде, DEBUG в проде) и **несколько сломанных мелочей** (bool-фильтры, пагинация хостов).
После P1-блока можно спокойно заниматься рефакторингом дублей — ничего «снежного кома» в коде нет.
