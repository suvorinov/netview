## 1. Архитектура — оценка

### Сильные стороны

- **Фабричный паттерн** (`create_app`) — стандарт Flask, корректная инициализация.
- **Blueprints** — чёткое разделение на 8 маршрутов + auth.
- **Базовый API-клиент** (`BaseApiClient`) — единая точка HTTP-вызовов с keep-alive через `requests.Session`.
- **Фабрики клиентов** (`factories.py`) — кэширование экземпляров на уровне приложения.
- **HTMX + Jinja2** — серверный рендеринг, минимум JS, быстрая интерактивность.
- **Параллельные запросы** на Dashboard (`ThreadPoolExecutor`) — правильный выбор для I/O-bound работы.
- **Fail-fast конфигурация** — проблемы с OPNsense видны в логе при старте.
- **Документация** — README подробный, код хорошо прокомментирован.

### Зоны риска

| Проблема | Серьёзность | Описание |
|---|---|---|
| Утечка памяти в rate-limiter | **Высокая** | `_login_failures` хранит таймстампы по IP, очищается только при обращении. При большом количестве уникальных IP память растёт без ограничений. |
| `time_ago` — naive/aware time | Средняя | Если API отдаёт naive-время (без tzinfo), `time_ago` считает его локальным временем сервера. На разных серверах результат будет разным. |
| Лимит 500 устройств | Средняя | `_device_counts_all()` и `export_html()` фетчат `limit=500`. При большей сети — неточные счётчики и обрезанный экспорт. |
| Таймауты не единообразны | Низкая | PrinterMonitor — 60s захардкожен, остальные клиенты — нет конфигурации через env. |
| Экспорт без пагинации | Низкая | `export_html()` генерирует до 500 записей в одном HTML. |

## 2. Безопасность — оценка

### Выполнено (хорошо)

- **Аутентификация** на всех маршрутах кроме `/login` и статики.
- **CSRF-защита** (flask-wtf) на всех POST/PUT/DELETE.
- **Session fixation** — `session.clear()` перед `login_user()`.
- **Open redirect** — проверка `next_url.startswith("/") and not next_url.startswith("//")`.
- **Rate limiting** — 5 попыток за 60 секунд с одного IP.
- **Cookie flags** — `HttpOnly`, `SameSite=Lax`, опциональный `Secure`.
- **SECRET_KEY** — если не задан, генерируется случайный (сессии сбрасываются).
- **Хеширование паролей** — поддержка pbkdf2 через werkzeug.
- **Constant-time сравнение** — `hmac.compare_digest` для паролей.
- **Protected MACs** — защита от блокировки критических устройств.

### Рекомендации

| # | Что | Действие |
|---|---|---|
| 1 | `_login_failures` утечка памяти | Добавить периодическую очистку (LRU или таймер) или ограничить размер dict. |
| 2 | Нет retry для OPNsense API | Добавить 1 retry с экспоненциальной задержкой для критических операций (block/unblock). |
| 3 | Экспорт данных через GET | `export_html()` и `export_blocked_report()` — нет CSRF. Для внутренней сети допустимо, но стоит учитывать. |

## 3. Качество кода

### Что хорошо

- **Единообразный стиль** — все файлы написаны в одном ключе, ruff-проверка проходит без замечаний.
- **Комментарии** — каждая неочевидная деталь документирована (OPNsense API, таймауты, cookie-флаги).
- **Обработка ошибок** — все `RequestException` ловятся в маршрутах, пользователь видит баннер «Сервис недоступен» вместо 500.
- **Шаблоны** — чистые Jinja2 + HTMX, без раздутого JS.
- **Тесты** — 211 тестов, включая unit-тесты утилит, интеграционные тесты маршрутов и тесты OPNsense-клиента с fake-сессией.

## 6. Готовность к продакшену (локальная сеть)

### Вердикт: **Да, можно запускать в prod (локальная сеть)**

Условия, при которых это безопасно:

1. **Внутренняя сеть** — сервис не доступен из интернета. Это ключевое условие: пароли хранятся в env, HTTPS не обязателен, rate-limiting базовое.

2. **Рекомендации перед запуском:**

| # | Действие | Приоритет |
|---|---|---|
| 1 | Задать `SECRET_KEY` явно (сгенерировать стабильный ключ) | Высокий |
| 2 | Задать `AUTH_USERS` с хешами паролей (не открытым текстом) | Высокий |
| 3 | Заполнить `DHCP_POOL` реальными значениями | Средний |
| 4 | Указать реальные URL сервисов (Printer, Host, LogSpy, NetCerber) | Высокий |
| 5 | При использовании HTTPS — включить `SESSION_COOKIE_SECURE=1` | Средний |
| 6 | Если сеть большая (>500 устройств) — увеличить лимит в клиентах | Низкий |

3. **Мониторинг:**

- Healthcheck в docker-compose настроен (`http://localhost:5000/`).
- Логи доступны через `make logs`.
- При недоступности сервисов — баннеры «Сервис недоступен» вместо падения страниц.

4. **Что НЕ нужно для локальной сети:**

- SSL/TLS termination (если используется только по HTTP внутри LAN).
- Rate limiting на уровне reverse proxy (базовый rate-limit на `/login` достаточен).
- Sharding / масштабирование (один экземпляр uvicorn покрывает потребности).

## 8. Заключение

**NetView — это зрелый, хорошо спроектированный внутренний инструмент.** Код чистый, документированный, покрыт тестами. Архитектура простая и предсказуемая (KISS). Для работы в локальной сети — полностью готов.

Главный риск — утечка памяти в rate-limiter при долгосрочной работе с большим количеством уникальных IP (минутное дело исправить). Второй риск — `IndexError` в одном HTMX-эндпоинте (тоже минутное дело).

Всё остальное — это обычные улучшения, которые можно делать постепенно после запуска.
